## Fraud Detection System — MongoDB Usage

This is an end-to-end fraud detection demo built almost entirely on MongoDB Atlas
capabilities. The database isn't just storage — it's the compute engine, search engine,
and stream processor all in one. All data lives in the `fraud_detection` database,
configured in `config/atlas-config.js:12`.

### Collections (the data model)

| Collection | Role |
|---|---|
| `transactions` | Source — every inserted doc triggers scoring via Stream Processing |
| `fraud_transactions` | Read model — flagged cases (score >= 70) + agent-written `investigation` subdoc + `text` field for vector embedding |
| `user_profiles` | Behavioral baselines (`avg_transaction_amount`, `frequent_locations`, `known_devices`) used to score anomalies |
| `chat_sessions` | Per-analyst conversation history with rolling LLM summaries; TTL index expires after 14 days (`src/server.js:338`) |
| `agent_memory` | Distilled conclusions from investigations + human analyst feedback (ground-truth signal for future cases) |
| `analysts` | Lightweight identity records upserted on login (`src/server.js:53`) |

### MongoDB Capability Usage

**1. Atlas Stream Processing** — `stream-processing/fraud-detection-pipeline.json`
A continuous aggregation runs on the `transactions` change stream. It `$lookup`s
`user_profiles`, evaluates three fraud signals (`high_amount`, `unusual_location`,
`new_device`) using `$cond`/`$concatArrays`, computes a weighted `fraud_score`, then
`$merge`s the result back into `transactions`. Score >= 70 -> flagged. This is
real-time scoring with no application code in the hot path.

**2. Vector Search with autoEmbed** — `indexes/fraud_transactions_text_index.json`
Uses Atlas's `autoEmbed` feature with the `voyage-4` model. Atlas generates embeddings
at write time on the `text` field — no client-side embedding call, no Voyage API key
in the app. Queries pass plain text to `$vectorSearch`. Used by both agents for
semantic "similar fraud cases" lookups (`src/agents/fraud-analyst-chat.js:88`,
`src/agents/fraud-investigation-stream.js:70`).

**3. Atlas Search (BM25 lexical)** — `indexes/fraud_transactions_lexical_index.json`
A static-mapping full-text index over merchant names, locations, device types, and
fraud indicators. Powers keyword-precise queries via `$search`.

**4. Hybrid Search via `$rankFusion`** — `src/agents/fraud-analyst-chat.js:51`
The default search mode combines the vector and lexical sub-pipelines using
Reciprocal Rank Fusion with weights 0.6/0.4. This is a single aggregation pipeline —
Atlas fuses the rankings server-side.

**5. Natural Language -> MQL** — `src/agents/fraud-analyst-chat.js:131`
The `run_aggregation` tool lets Claude generate a MongoDB aggregation pipeline from
plain English and execute it directly against Atlas. It's sandboxed: only 3 allowed
collections, blocks `$out`/`$merge`/`$indexStats` etc., and caps results at 50. The
model sees the result set, not a raw data dump.

**6. Document model** — Nested fraud indicators, device metadata, merchant info, and
investigation notes all live in a single document. The agent updates nested fields via
dot notation (`'investigation.notes'`, `'investigation.routed_to_human'`) in
`src/agents/fraud-investigation-stream.js:112`.

**7. Aggregation framework** — Used heavily: `$lookup` for user enrichment,
`$addFields`/`$cond` for scoring, `$merge` for write-back,
`$vectorSearch`/`$search`/`$rankFusion` for retrieval, `$project`/`$limit` for shaping.

**8. Indexes** — Created in `scripts/generate-sample-data.js:213`:
`{user_id, timestamp}`, `{status}`, `{timestamp}`, a `2dsphere` geospatial index on
`location.coordinates`, plus unique indexes on `user_profiles`.

**9. TTL index** — `chat_sessions` auto-expires idle sessions after 14 days
(`src/server.js:338`).

### Connection Pattern

Each request creates a fresh `MongoClient`, connects, does its work, and closes in a
`finally` block. This is a demo-friendly pattern (no shared pool across the Express
process) — visible in every route handler and tool. The config declares
`maxPoolSize: 10` and standard timeouts in `config/atlas-config.js:28`.

### In short
MongoDB here is five products in one: operational database, real-time stream
processor, vector search engine, lexical search engine, and the execution backend for
LLM-generated queries. The application layer is a thin Express server plus two
LangChain agents whose "tools" are essentially MongoDB queries.

is no `langgraph-checkpoint-mongodb` package present. So no LangGraph MongoDB

## Memory Architecture

The project implements two distinct memory tiers, both backed by MongoDB but with
different lifecycles, scopes, and purposes.

### Short-Term Memory — `chat_sessions` collection

**Scope:** a single analyst's active conversation with the chatbot agent.

**Mechanism** (`src/server.js:113-181`):
1. Each analyst gets one persistent session keyed by `analyst_id` (derived from login
   email/name).
2. The session document stores a `messages` array (the verbatim user/assistant turns)
   plus a rolling `summary` field.
3. On every chat turn, the new user message + agent reply are `$push`ed into
   `messages` (`src/server.js:160`).
4. A sliding window of 20 messages (`SESSION_WINDOW`) is enforced by `trimSession()`
   (`src/server.js:94`). When the buffer overflows, the oldest excess messages are sent
   to Claude with a summarization prompt (`summarizeConversation` in
   `fraud-analyst-chat.js:317`), which produces a 2-4 sentence rolling summary. That
   summary replaces the old one, and the verbatim overflow is trimmed off.
5. At the start of the next turn, the summary is reinjected as a synthetic `user`
   message: `[Earlier conversation summary]: ...` (`src/server.js:142`), prepended to
   the remaining verbatim history.

**Lifecycle:** a TTL index on `updated_at` with `expireAfterSeconds: 14 days`
(`src/server.js:338`) auto-deletes idle sessions. Active conversations stay; abandoned
ones decay.

**Result:** the agent remembers the gist of a long conversation without unbounded
context-window growth — recent detail verbatim, older context compressed.

### Long-Term Memory — `agent_memory` collection

**Scope:** cross-session, cross-agent, persistent institutional knowledge — distilled
conclusions, not raw transactions.

**Two sources of writes:**

| Source | Written by | Trust level |
|---|---|---|
| `source: "agent"` | Investigation agent's `write_investigation_findings` tool (`fraud-investigation-stream.js:126`) via `buildInvestigationMemory()` | Unverified prior reasoning — precedent, not fact |
| `source: "human_confirmed"` | The analyst feedback endpoint (`server.js:305`) when a human reviews a case and marks it `confirmed_fraud` or `false_positive` | Ground truth |

Each memory document has: `type`, `transaction_id`, `user_id`, `summary` (the
natural-language conclusion), `tags` (fraud indicators), `outcome`, `source`,
`created_at`.

**Retrieval** (`agent-memory-tool.js:11`):
- The `search_agent_memory` tool runs a `$vectorSearch` against the `agent_memory`
  collection using an autoEmbed index on the `summary` field
  (`indexes/agent_memory_text_index.json`, `voyage-4` model).
- A `verified_only` flag lets the agent filter to just `human_confirmed` memories when
  it specifically needs ground truth rather than precedent.
- The tool description explicitly coaches the model on the epistemic difference:
  human-confirmed = fact, agent = unverified reasoning to weigh.

**Both agents use it:**
- The analyst chatbot includes it as one of its 4 tools (`fraud-analyst-chat.js:222`)
  and the system prompt instructs it to check memory alongside raw case search for
  "is this actually fraud?" questions.
- The investigation agent includes it as step 4 of its 5-step protocol
  (`fraud-investigation-stream.js:157`), checking past conclusions before writing its
  own.

### How the two tiers interact

    Short-term (per analyst, ephemeral)         Long-term (shared, persistent)
    -------------------------------           ------------------------------
    chat_sessions.messages[]                    agent_memory.summary
      + chat_sessions.summary                     (vector-embedded, searchable)
      |                                           ^
      | rolling compression                       | writes from:
      | via summarizeConversation()               |   1. agent conclusions (source: agent)
      |                                           |   2. human feedback (source: human_confirmed)
      v                                           | never expires
      TTL: 14 days auto-expire                    |
                                                  |
                      read by both agents via search_agent_memory tool

The key design insight: short-term memory is conversational state (who said what,
compressed over a sliding window), while long-term memory is distilled institutional
knowledge (what was concluded and whether a human verified it). The `source` field on
long-term memories creates a trust gradient — the agent knows which past conclusions
are facts and which are just its own prior reasoning.

### What the integration packages actually offer

`@langchain/mongodb` (v1.3.0, official LangChain.js) exports five modules:

| Export | What it wraps |
|---|---|
| `MongoDBAtlasVectorSearch` | `$vectorSearch` — `similaritySearch`, `similaritySearchWithScore`, `addDocuments`, `delete`, MMR, pre/post filters, auto-embed mode, `$rerank` |
| `MongoDBChatMessageHistory` | `BaseListChatMessageHistory` — `getMessages`, `addMessage`, `clear` (stores messages array in one doc keyed by `sessionId`) |
| `MongoDBCache` | LLM response cache backed by a MongoDB collection |
| `MongoDBStore` | Generic key-value `BaseStore` |
| Voyage embeddings helper | Client-side Voyage embedding (not needed here — autoEmbed is used) |

### Mapping each MongoDB usage to a potential integration

| # | Current usage | File | LangChain equivalent | Fit |
|---|---|---|---|---|
| 1 | Vector search for similar fraud cases | `fraud-investigation-stream.js:62` | `MongoDBAtlasVectorSearch.similaritySearchWithScore` (auto-embed mode) | Good |
| 2 | Vector-only search mode in chatbot | `fraud-analyst-chat.js:88` | Same | Good |
| 3 | Hybrid search (`$rankFusion`) | `fraud-analyst-chat.js:51` | None — no `$rankFusion` support | No fit |
| 4 | Lexical search (`$search` BM25) | `fraud-analyst-chat.js:39` | None — no Atlas Search wrapper | No fit |
| 5 | `agent_memory` vector search | `agent-memory-tool.js:17` | `MongoDBAtlasVectorSearch` (auto-embed, different collection) | Good |
| 6 | Chat session message storage | `server.js:113-181` | `MongoDBChatMessageHistory` | Partial |
| 7 | Session rolling summary + sliding window trim | `server.js:94-110` | None | No fit |
| 8 | LLM-generated aggregation execution | `fraud-analyst-chat.js:131` | None — this is raw MQL by design | No fit |
| 9 | User risk profile (3 parallel reads) | `fraud-analyst-chat.js:188` | None | No fit |
| 10 | Investigation write-back (`findOneAndUpdate` on nested doc) | `fraud-investigation-stream.js:112` | None | No fit |
| 11 | Transaction insert, login upsert, feedback, case listing | `server.js` various | None | No fit |
| 12 | Stream Processing pipeline | `stream-processing/*.json` | None — Atlas ASP is server-side | No fit |

Score: 3 of 12 usages have a clean fit. 1 has a partial fit. 8 have no LangChain
equivalent.

### Detailed analysis of the viable migrations

#### 1. MongoDBAtlasVectorSearch — for the three pure vector searches

The three `$vectorSearch` calls could become 3 lines instead of 15.

What you gain:
- Less boilerplate, no manual `$vectorSearch` pipeline construction
- `Document` objects with `pageContent`/`metadata` separation
- MMR diversity search becomes a one-liner
- Built-in `$rerank` support

What you lose:
- Custom `$project`: The current code projects specific fields. The integration
  returns `Document` objects where everything except `text` is stuffed into
  `metadata`. You'd need to re-flatten.
- `numCandidates` ratio control: The integration hardcodes `numCandidates: 10 * k`.
- The `model: 'voyage-4'` parameter: The integration's auto-embed mode uses
  `query: { text: query }` format — actually an improvement.

#### 2. MongoDBChatMessageHistory — for short-term memory (partial)

The current `chat_sessions` system does four things:
1. Store messages array <- this is what the integration covers
2. Maintain a rolling LLM-generated `summary` <- not covered
3. Trim to a 20-message sliding window <- not covered
4. Auto-expire via TTL index <- not covered

`MongoDBChatMessageHistory` gives you `addMessage` and `getMessages` — that's it.
Verdict: marginal benefit, adds a constraint, doesn't reduce the complex part.

#### 3. MongoDBCache — not currently needed

Could be added as a future optimization, but that's a feature addition, not a
migration.

### The migrations that can't happen

The core differentiating features of this project cannot use LangChain integrations
because they're deliberately raw MongoDB:

- `run_aggregation` tool: LLM generates arbitrary MQL pipelines at runtime. No
  LangChain abstraction wraps this.
- Hybrid search (`$rankFusion`): No support. Migrating would lose the default search
  mode.
- Lexical search (`$search` BM25): No Atlas Search wrapper exists.
- Investigation write-back: Domain-specific CRUD on nested document fields.
- Agent memory writes: Domain-shaped documents with `source`, `tags`, `outcome`.
- Stream Processing: Server-side Atlas feature.
- User risk profile, transaction insert, login, feedback, case listing: Standard
  operational CRUD.

### Architectural concerns with the migration

1. Dual-pattern fragmentation: Two ways of talking to MongoDB.
2. Connection management mismatch: Project creates fresh MongoClient per request;
   integration implies long-lived client.
3. The Document abstraction leaks into agent tool results: Need mapping step.
4. agent_memory has a trust gradient that doesn't fit VectorStore.

### Recommendation

Don't migrate. A targeted migration of the 3 pure `$vectorSearch` calls is
technically clean but yields ~30 lines of savings while introducing dual patterns,
connection-lifecycle mismatch, and a Document-to-flat-JSON mapping tax. The project's
MongoDB usage is deliberately close to the metal.

Higher-value refactors:
- Extract a shared `getDb()` helper (eliminates repeated MongoClient boilerplate)
- Extract a `vectorSearch()` helper for the 3 vector search calls
- Keep the raw driver for everything else

USER: Can this project and application be converted to langgraph with mongodb
integration

ASSISTANT:

Yes — technically every system built on tool-calling LLMs can be converted to
LangGraph. The real question is whether the conversion adds value or just replaces
working code with framework overhead.

### What the conversion looks like, component by component

#### 1. Both agents -> createReactAgent

The current agents are hand-rolled ReAct loops. That's exactly what `createReactAgent`
replaces.

Current (fraud-analyst-chat.js:286-308):
```javascript
for (let turn = 1; turn <= 10; turn++) {
  const response = await model.invoke(messages);
  messages.push(response);
  const toolCalls = response.tool_calls ?? [];
  if (toolCalls.length === 0) {
    yield { type: 'token', text: extractText(response.content) };
    yield { type: 'done' };
    return;
  }
  for (const tc of toolCalls) {
    yield { type: 'status', text: statusLabel(tc.name, tc.args) };
    const match = TOOLS.find((t) => t.name === tc.name);
    const result = await match.invoke(tc.args);
    messages.push(new ToolMessage({ content: result, tool_call_id: tc.id }));
  }
}
```

Converted:
```javascript
const { createAgent } = require('langchain');

const analystAgent = createAgent({
  llm: new ChatAnthropic({ model: 'claude-sonnet-4-6', thinking: { type: 'adaptive' } }),
  tools: [searchFraudCasesTool, runAggregationTool, getUserRiskProfileTool, searchAgentMemoryTool],
  prompt: (state) => {
    const modeInstruction = `\n\nSearch mode preference: use mode: "${state.searchMode}"...`;
    return [new SystemMessage(SYSTEM_PROMPT + modeInstruction), ...state.messages];
  },
  checkpointSaver: mongoSaver,
  store: mongoStore,
  preModelHook: messageTrimmingNode,
});
```

What this gives you:
- The tool-call loop, message appending, and turn counting become framework concerns
- Built-in .stream() with streamMode: 'values', 'updates', or 'messages'
- preModelHook is the designated slot for message trimming/summarization

What it costs:
- The custom SSE event shape is replaced by LangGraph's stream event shape
- The investigation agent's fixed 5-step protocol is currently prompt-enforced. In
  LangGraph you could model this as an explicit StateGraph — this is the one place
  where LangGraph is genuinely better

#### 2. Short-term memory -> MongoCheckpointSaver

With langgraph-checkpoint-mongodb, LangGraph automatically checkpoints the full state
after every super-step into `checkpoints` and `checkpoint_writes` collections.

What you gain:
- Time travel: retrieve any past checkpoint by ID
- Resumability: crash recovery, resume from last checkpoint
- Thread isolation: thread_id maps naturally to analyst_id

What you lose / the gaps:
- Rolling summary: LangGraph doesn't do this automatically. Implement as preModelHook.
- TTL expiry: Checkpoint collections don't have TTL. Add yourself or run cleanup job.
- Queryability: Checkpoint data is base64-encoded serialized bytes. Can't inspect
  directly.
- The checkpointer is a net win for robustness but requires rebuilding summarization
  logic as a preModelHook and adding your own TTL.

#### 3. Long-term memory -> BaseStore + MongoDBStore

The mismatch:
- BaseStore is a generic key-value store. The agent_memory collection has rich domain
  fields (source, tags, outcome) core to reasoning.
- The verified_only filter is domain-specific.
- The human feedback endpoint writes from outside the agent loop.

Verdict: marginal benefit. The store abstraction fights the domain model.

#### 4. Streaming -> LangGraph .stream()

Use streamMode: ['messages', 'updates'] then map to existing SSE event types.
Cost: frontend SSE handlers need an adapter layer.

#### 5. The MongoDB-specific features that don't change

- run_aggregation (LLM-generated MQL): stays as custom tool
- Hybrid search ($rankFusion): no LangGraph support
- Lexical search ($search BM25): no support
- Stream Processing: server-side Atlas feature
- Transaction insert, login, feedback, case listing: Express CRUD routes
- Investigation write-back: domain-specific MongoDB update

### The honest cost-benefit

| Factor | Current (hand-rolled) | LangGraph + MongoDB |
|---|---|---|
| Agent loop code | ~25 lines x 2 agents, manual | Delegated to createReactAgent |
| Tool definitions | Unchanged | Same |
| Streaming | Custom typed SSE events | .stream() + adapter to SSE |
| Short-term memory | chat_sessions + rolling summary + TTL | MongoCheckpointSaver + preModelHook + manual TTL |
| Crash recovery | None | Automatic |
| Time travel | None | Full checkpoint history |
| Long-term memory | Direct agent_memory collection | Same, optionally wrapped in BaseStore |
| Investigation protocol | Prompt-enforced 5-step sequence | Code-enforced graph topology (the real win) |
| Hybrid/lexical search | Custom tool | Custom tool (no change) |
| Frontend | Consumes custom SSE events | Needs adapter or rewrite |
| New dependencies | @langchain/langgraph (present), langgraph-checkpoint-mongodb (10 weekly downloads, third-party) | Risk: unmaintained checkpointer |

### The decisive factors

In favor of converting:
1. The investigation agent's 5-step protocol is currently prompt-enforced. Converting
   to an explicit StateGraph turns "hope the LLM follows the steps" into "the graph
   topology makes skipping a step impossible."
2. Crash recovery and resumability.
3. Checkpoint history for audit/rewind.

Against converting:
1. The checkpointer package is a risk (~10 weekly downloads, third-party, a year old).
2. Most of the project's MongoDB usage doesn't benefit.
3. The short-term memory system gets more complex, not less.
4. Frontend rewiring needed.

### Recommendation

Do a partial conversion, not a full one:

1. Convert the investigation agent to an explicit StateGraph — the real win. The 5-step
   protocol becomes a code-enforced graph with sequential nodes.
2. Keep the analyst chatbot as createReactAgent — it's free-form conversational.
3. Use MongoCheckpointSaver for both agents — accept the maintenance risk, or write a
   minimal BaseCheckpointSaver (~200 lines).
4. Don't use BaseStore/MongoDBStore for long-term memory. Keep agent_memory as a direct
   collection.
5. Don't touch the tools. Hybrid search, lexical search, run_aggregation, write-back,
   user risk profile — all stay as custom tools.
6. Add a stream-event adapter in Express routes.

This gives you the protocol enforcement and crash recovery benefits while keeping the
MongoDB-specific intelligence as raw driver calls — which is where it belongs.
